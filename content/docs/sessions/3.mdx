## 개념

### 왜 AI와 일할수록 버전 관리가 필수인가

- AI는 한 번에 여러 파일을 빠르게 고칩니다. 잘되던 기능이 다른 요청 때문에 깨지는 일이 흔합니다.
- Claude Code에도 되돌리기(`/rewind`)가 있지만, 공식 문서도 "Git을 대신하지 않는다"고 밝힙니다. 명령으로 바뀐 파일이나 다른 사람과의 공유는 추적하지 못합니다 ([Best practices](https://code.claude.com/docs/en/best-practices)).
- 바이브 코딩과 에이전틱 엔지니어링을 가르는 **첫 번째 안전장치**가 바로 이것입니다.

## 협업 관점의 Git과 GitHub

지금까지는 **혼자** 쓰는 Git이었습니다. 하지만 업무 도구는 결국 팀이 함께 씁니다. "출장비 계산기를 옆 팀도 고쳐 쓰고 싶대요", "담당자가 바뀌어서 인수인계해야 해요" — 이때 Git과 GitHub의 진짜 힘이 나옵니다.

<Analogy title="공유 드라이브의 '최종본' 전쟁 vs GitHub">
  공유 드라이브에서 두 사람이 같은 엑셀을 동시에 고치면, 나중에 저장한 사람이 앞사람의 수정을 덮어씁니다. 그래서 "최종_김주무관", "최종_이주무관 수정"이 생기죠. GitHub에서는 각자 <b>사본(브랜치)</b>에서 고치고, <b>기안(풀 리퀘스트)</b>을 올려 검토받은 뒤, <b>결재(머지)</b>가 끝난 것만 원본(main)에 반영됩니다. 덮어쓰기가 없고, 누가 언제 무엇을 왜 바꿨는지 모두 남습니다.
</Analogy>

### 협업에 필요한 개념 6가지

| 개념 | 뜻 | 행정 비유 |
| --- | --- | --- |
| <Term id="collaborator">협업자</Term> | 비공개 저장소에 초대받은 사람 | 서류철 열람·수정 권한 부여 |
| <Term id="clone">클론</Term> / <Term id="pull">풀</Term> | 저장소를 내려받기 / 남이 올린 최신 변경 받아오기 | 사본 받기 / 최신 문서대장 받아 오기 |
| <Term id="branch">브랜치</Term> | 원본(main)을 건드리지 않는 작업 사본 | 수정안 초안 |
| <Term id="pull-request">풀 리퀘스트</Term> (PR) | "내 수정안을 원본에 합쳐 주세요" 요청 + 검토 창구 | 기안 올리기 |
| <Term id="code-review">코드 리뷰</Term> → <Term id="merge">머지</Term> | 동료가 읽고 의견 → 승인 후 원본에 반영 | 검토·협조 → 최종 결재 |
| <Term id="issue">이슈</Term> | 할 일·버그·요청을 저장소에 남기는 기록 | 업무 요청 대장 |

### 함께 일하는 기본 흐름

<Steps>
<FdStep>
**최신으로 맞추기 (pull)** — 작업 시작 전에 동료가 올린 변경을 먼저 받아 옵니다. 오래된 사본에서 일하는 것이 충돌의 가장 큰 원인입니다.
</FdStep>
<FdStep>
**브랜치 만들기** — `fix-hotel-limit`처럼 무엇을 할지 드러나는 이름으로 사본을 만듭니다. main(원본)은 늘 "결재 끝난, 잘 돌아가는 상태"로 둡니다.
</FdStep>
<FdStep>
**고치고 커밋** — 혼자 쓸 때와 똑같습니다. 기능 하나 = 커밋 하나.
</FdStep>
<FdStep>
**푸시하고 풀 리퀘스트** — 무엇을, 왜 바꿨는지, 검토자가 무엇을 확인하면 되는지 적습니다. 기안문의 "제목·목적·검토 요청 사항"과 같습니다.
</FdStep>
<FdStep>
**검토 → 머지** — 동료가 바뀐 줄을 보고 댓글을 남기고, 괜찮으면 승인해서 main에 합칩니다. 다 쓴 브랜치는 지웁니다.
</FdStep>
</Steps>

<Callout title="이 흐름이 다음 회차와 바로 이어집니다">
  4회차에 GitHub를 Vercel에 연결하면, **main에 머지되는 순간 실제 사이트가 자동으로 바뀝니다.** 풀 리퀘스트를 올리면 그 수정안만 담은 **미리보기 주소**도 따로 생겨서, 검토자가 실제 화면을 눌러 보고 결재할 수 있습니다. "결재 끝난 것만 원본에 반영"이 곧 "검증된 것만 서비스에 반영"이 됩니다.
</Callout>

### 충돌은 사고가 아니라 알림

두 사람이 **같은 파일의 같은 줄**을 서로 다르게 고친 뒤 합치려 하면 Git이 멈추고 묻습니다. "둘 중 무엇을 남길까요?" 이것이 <Term id="conflict">충돌</Term>(conflict)입니다.

- 저장소가 망가진 것이 아닙니다. 다른 부분을 고친 변경은 Git이 알아서 합칩니다. 같은 줄만 사람에게 묻는 것입니다.
- 어느 쪽이 맞는지는 **내용을 아는 사람**이 정합니다. Claude Code에게 "양쪽을 나란히 보여 줘"라고 하고, 고르는 것은 내가 합니다.
- 충돌을 줄이는 습관: **시작 전 pull**, **브랜치는 작게, 자주 머지**, **같은 파일을 동시에 크게 고치지 않기**(이슈로 담당을 나누기).

<PromptCard id="conflict-resolve" compact />

### AI와 함께하는 팀 협업

AI가 코드를 빠르게 많이 만들수록 <b>"사람이 검토하고 결재한다"</b>는 단계가 더 중요해집니다. GitHub의 협업 흐름은 그 단계를 자연스럽게 만들어 줍니다.

| 일 | Claude Code에게 맡길 것 | 사람이 할 것 |
| --- | --- | --- |
| 수정안 만들기 | 브랜치 생성, 수정, 커밋, 풀 리퀘스트 작성 | 무엇을 바꿀지 정하기 |
| 1차 검토 | 바뀐 내용 요약, 빠진 점·위험한 점·비밀 정보 점검 | 의견을 골라 댓글로 남기기 |
| 충돌 | 부딪힌 부분을 나란히 보여 주기, 고른 대로 정리 | 어느 쪽을 남길지 결정 |
| 결재 | — | **머지 버튼은 사람이 누른다** |

- Claude Code는 터미널의 `gh`(GitHub CLI)로 저장소 만들기, 초대, 풀 리퀘스트, 이슈를 대신 처리합니다. 화면을 찾아 헤맬 필요가 없습니다.
- 한 걸음 더 나가면, GitHub의 이슈나 풀 리퀘스트에 `@claude`라고 댓글을 달아 Claude에게 일을 맡기는 방식도 있습니다 ([Claude Code GitHub Actions](https://code.claude.com/docs/en/github-actions)). 이 과정에서는 다루지 않지만, 개발 팀들이 실제로 쓰는 흐름입니다.
- **CLAUDE.md는 저장소와 함께 공유됩니다.** 팀 규칙(브랜치로 작업, 한글 커밋 메시지, 비밀 파일 금지)을 적어 두면 팀원 모두의 Claude Code가 같은 규칙을 따릅니다.

### 팀 저장소 안전 규칙

<Callout type="warn" title="업무 저장소에서 꼭 지킬 것">
  ① 저장소는 **비공개**, 필요한 사람만 협업자로 초대합니다. ② `.env`·개인정보 파일은 처음부터 .gitignore에. ③ main은 **보호 브랜치**로 설정해 검토 없이 바로 바뀌지 않게 합니다 ([보호된 브랜치 정보](https://docs.github.com/ko/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches)). ④ 담당자가 바뀌면 협업자 목록에서 권한을 정리합니다. 인사 발령 때 시스템 권한을 회수하는 것과 같습니다.
</Callout>

<DeepDive title="요즘 업계에서는 — 숫자로 보는 GitHub 협업">

- GitHub에서 일하는 개발자는 **1억 8천만 명 이상**이고, 2025년 한 해 동안 매달 평균 **4,320만 건의 풀 리퀘스트가 머지**되었습니다(전년 대비 23% 증가). 커밋은 한 해 **약 10억 건**이 올라왔습니다 ([GitHub Octoverse 2025](https://github.blog/news-insights/octoverse/octoverse-a-new-developer-joins-github-every-second-as-ai-leads-typescript-to-1/)).
- 늘어난 활동의 큰 부분이 AI와 함께 만든 코드입니다. 그래서 개발 조직들은 "AI가 만들고 → 풀 리퀘스트로 올리고 → 사람이 검토해 머지"하는 흐름을 표준으로 삼고 있습니다. 기안 → 검토 → 결재라는 익숙한 행정 절차가 소프트웨어 협업의 기본 구조와 같습니다.
- 개발자가 아니어도 이 흐름은 그대로 쓸 수 있습니다. 문서·데이터·업무 도구를 저장소로 관리하면, 인수인계 때 "무엇을 왜 바꿨는지"가 이력으로 고스란히 넘어갑니다.

</DeepDive>
